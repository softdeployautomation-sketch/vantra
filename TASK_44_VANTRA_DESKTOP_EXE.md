## What already exists (grounded — verified in the current codebase, not assumed)

- **SpaceWorker's Extractor EXE is the proven pattern to follow.** Real, tested, shipped this session: a Tauri shell spawning a bundled Next.js standalone server locally (`scripts/runtime-assemble.mjs` in the spaceworker repo), a real Windows CI build pipeline (`.github/workflows/build-exe.yml`), and a license-gate component (`components/license-gate.tsx`) with a 24h silent trial → gate on expiry. **`EXE_BUILD_LESSONS_LEARNED.md`** in the spaceworker repo documents every real bug hit building it (the `Builder::build()` vs `.run()` bug — total failure, no window ever shown; the `.ts` source leak; the NSIS `_up_` path quirk; Windows `node.exe` needing its full dist bundled; layout bugs only reproducing at the real window size; CI-builds-from-`origin/main` catching us out repeatedly). **Read it before starting this** — it exists specifically so these don't get rediscovered from scratch.
- **Single-device remote cmd/PowerShell execution already exists** as a customer-facing (premium) feature: `app/api/devices/[agentId]/cmd/route.ts` (ad-hoc shell command), `app/api/devices/[agentId]/queue-command/route.ts`, and a named-script runner (`app/api/devices/[agentId]/scripts/[scriptId]/run/route.ts`, gated by `lib/script-authz.ts`'s `canRunScriptOnAgent`). **The mechanism is not new** — what's new is admin-level access to any customer's device (not just the device owner's own), and bulk (nothing does that today).
- **No auto-update mechanism exists anywhere in this codebase.** Genuinely new.
- **The admin ticket view already shows the submitter's email** on both the list and detail pages (`app/admin101/(protected)/tickets/page.tsx` and its `[ticketId]` detail page, built earlier this session for Task 41's companion ticket-assignment work) — `t.user.email` is already rendered. This specific display requirement is already satisfied; see the auth section below for what's actually missing.
- **SpaceWorker's own EXE licensing scheme is being extended right now** (separate, already-queued task) to add a `product` tag to the signed license payload and enforce it against the running build's own identity at activation. Vantra's EXE licensing should very likely reuse the exact same scheme (same signing math, same admin generator, different `product` value) — **but sharing one signing secret across two separate apps/repos is a real security-boundary decision that needs an explicit yes from the owner**, not a default assumption. Compromise of one app's signing secret would let someone forge licenses for the other too.

## Confirmed answers (owner, 2026-09-18)

1. **Local DB is real, not a cache.** Devices added through the desktop app are saved to a real local database on the user's own machine — the app works independently of Vantra's backend for normal device management/viewing. The **only** backend dependency is installer generation (provisioning a new device's TRMM client/site, calling the MSI/ZIP generator) and anything else that's deliberately server-managed and not meant to be user-editable. The web's own database becomes a **backup/mirror** for desktop users — their data still reaches Vantra's servers, just not as the primary read/write path anymore.
2. **Bulk remote execution: admin-only, scoped to one customer's own device set at a time.** The stated use case is literal: a customer has 4 devices, admin helps move all 4 (or one at a time) to a different staff member for a fix, or runs a command across them. **No cross-customer bulk** — never touches more than one customer's fleet in a single action. **No staff access at all** — admin-only, full stop ("No staff have that access. Customer already have what they need.").
3. **Auto-update: both automatic and manual.** A background auto-update check, plus an explicit "Check for updates" button in Settings — same place the license status/activation lives, so Settings becomes the one place a desktop user manages their installed app's state (license + updates).
4. **Desktop-mode auth is email + license key, not a traditional password session.** This is the load-bearing detail: the EXE does NOT reuse the web's session-cookie/password login. It authenticates the same way SpaceWorker's own EXE does — a license key tied to a `licensee` email, validated (initially offline against the embedded signing secret, same pattern). This has a real consequence: **a ticket submitted from inside the EXE needs its own lightweight submission surface** (there's no "submit a ticket" UI inside the EXE today, and the web's `/dashboard/support` won't be shown to desktop-mode users per requirement #9 below) — resolved server-side by matching the license's email to the user's real, already-existing `User` account. The admin-side email display is already done (see above); the EXE-side submission surface is the actual gap.

## Requirements, organized from the ask

1. **Downloadable Vantra EXE** — same build pattern as SpaceWorker's Extractor: Tauri shell, bundled Next.js standalone server, real Windows CI build. **Eligibility, confirmed by owner (2026-09-18): premium customers OR staff** — `Organization.plan === "premium"` (a user's premium status comes from their active org, not a direct user field) or `User.isStaff === true`. Free-tier, non-staff accounts don't get EXE access. Staff need it too — not just paying customers — since device work (including the planned bulk remote execution, req #11) happens from the EXE. Enforce this at the admin license-issuance route (`app/api/admin/exe-licenses/route.ts`'s `handleIssue`) now that it exists — reject issuing a key to an account that's neither premium nor staff, with a clear message. When self-service issuance is eventually built (not yet — issuance is admin-only today), the same check applies there too.
2. **Real local DB on the user's machine** — confirmed above. This is the single biggest build in this whole task: local schema, local read/write for devices (and presumably tickets, settings, whatever else desktop mode surfaces), plus a sync path to the cloud DB as backup. Needs its own detailed design pass before implementation — don't start coding this from just this doc's description; scope the actual local schema, what syncs and how often, and conflict handling (two Vantra installs for the same account, or an install plus the web dashboard both writing) as a dedicated first step.
3. **Account flips to "desktop mode"** on first EXE login (email + license, confirmed above). From that point, web access for that account narrows to: generating more licenses, topping up account balance. Confirm explicitly (not yet answered) whether that narrowing is absolute (no ticket/support access via web at all) or specifically about the Devices/dashboard surface — the auth-model answer strongly implies "no web session at all really applies once in desktop mode" but get this confirmed before building the access-gating logic, since it's easy to build too strict or too loose.
4. **Feature parity** — "should work exactly how the web works now." Full breadth, not a narrow tool.
5. **Own branding/domain** — looks and feels like Vantra, hits Vantra's real API, not a white-label shell.
6. **Installer generation and other server-managed operations stay backend-only** — confirmed above, the one thing that always calls home.
7. **Auto-update** — confirmed above, background + manual button.
8. **License gate** — same style as SpaceWorker's, trial → gate, admin-generatable via Vantra's own separate generator (see below — confirmed as its own secret/UI, not shared with SpaceWorker's).
9. **Website hidden from desktop-mode users** beyond the two carved-out billing/licensing actions.
10. **Admin retains full device visibility** — unchanged, already true today.
11. **NEW: admin bulk remote cmd/PowerShell execution**, confirmed scope above (admin-only, single-customer-scoped, single or bulk within that customer's own devices).
12. **License-activation UI in Settings** for both the SpaceWorker Extractor (separate, already-queued quick task) and this Vantra EXE from day one.
13. **Real VM testing** after every build — same discipline as every EXE deliverable this session: build in CI, independently verify the artifact (no leaked source/secrets — reuse the exact checklist from `EXE_BUILD_LESSONS_LEARNED.md`), then real install + click-through on the Windows VM before anything is called done.

## Confirmed: separate generator, separate secret (owner, 2026-09-18)

Vantra gets its own license generator and its own signing secret — not shared with SpaceWorker's EXE scheme. Follow the exact same code pattern (payload shape, HMAC signing, admin generator UI) as SpaceWorker's `lib/exe-license.ts` and its admin generator once that's built, but with Vantra's own `EXE_LICENSE_SECRET`-equivalent env var and its own admin route/UI in this repo. This closes the security-boundary concern raised above — a leaked secret in one app can never forge licenses for the other.

## Suggested build order

1. **Local-DB architecture design** — a dedicated design pass (schema, sync direction/frequency, conflict handling) before any code. This is the highest-risk, highest-cost part of the whole task; get it right on paper first.
2. **License-activation-in-Settings** for the Vantra EXE build target — small, same pattern as the SpaceWorker Settings task, do early since it's needed regardless of how the bigger pieces resolve.
3. **EXE packaging** (Tauri shell + bundled standalone server + Windows CI build) using the `EXE_BUILD_LESSONS_LEARNED.md` checklist from day one.
4. **Email+license auth path** (distinct from the web's password session) + license gate + Vantra's own separate admin generator (own secret, own UI, same pattern as SpaceWorker's).
5. **Local DB implementation** against the design from step 1, starting with devices only (the concretely-named case), expanding to other surfaces once that's proven.
6. **"Desktop mode" account-state switch** + narrowed web access + the EXE-side ticket-submission surface.
7. **Admin bulk remote-execution** — single-customer-scoped, admin-only, with a real confirmation step showing exactly how many devices will be affected before it runs.
8. **Auto-update** (background + manual button) — last, since it depends on a stable, already-shipping EXE to update.

Each step is independently shippable and testable. Real Windows VM testing after every build, not just at the end — same as every EXE deliverable this session.
