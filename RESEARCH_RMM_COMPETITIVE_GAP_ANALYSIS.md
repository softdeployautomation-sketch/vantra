# Vantra vs. Commercial RMM Tools — Competitive Gap Analysis

*Prepared 2026-09-04. Grounded in a direct read of the shipped codebase (`app/dashboard/**`, `components/*.tsx`, `lib/trmm.ts`, `prisma/schema.prisma`) — not the plan document's "next steps" language, which is frequently stale relative to what Cline has actually since shipped. Where the plan doc said "not yet implemented," the live schema/components were checked and, in several cases, the feature turned out to already be live (multi-org, wallet, org switcher). Competitor research via web search, sourced inline.*

## 1. Summary

Vantra is **not actually feature-thin** — it already has multi-org/MSP support, a wallet+manual-crypto billing system, device groups, a customer script manager, remote desktop/terminal/file tools, an admin panel with service controls and payment review, Telegram notifications, and a full ticket system. Measured by checklist-of-features, it's closer to a mid-tier commercial RMM than a v1 prototype.

The "looks empty and scanty" reaction is real anyway, and it traces to two concrete, fixable things rather than a lack of capability:

1. **The two screens a user looks at 90% of the time are informationally thin.** The dashboard home (`/dashboard`) is a device list and nothing else — no KPI row, no alert feed, no "what needs attention today" summary. The device detail Overview tab renders 7 plain text rows and 4 check-count tiles — it does not surface `total_ram`, `disks`, or installed-software counts even though `lib/trmm.ts`'s `AgentDetail` type already documents these fields exist in the live TRMM response. This is the single biggest driver of the "scanty" impression: commercial RMMs make their device/overview pages feel dense with live telemetry (health scores, charts, patch compliance, asset specs); Vantra's equivalent screens are closer to a static form.
2. **Real, already-built capability is buried or gated in a way that hides it.** Task Manager (process kill), Windows service control, and installed-software management all exist and are fully wired (`lib/trmm.ts`'s `listAgentProcesses`/`killAgentProcess`/`getInstalledSoftware`/`installSoftwareViaChoco`/`listWindowsServices`/`controlWindowsService`, each with a live API route) — but they only surface three clicks deep, inside the Remote Tools tab's "Backstage" panel, which itself is gated behind the Premium plan. A free-tier user, or anyone who hasn't opened Remote Tools, would never know these exist. Commercial tools show at least a read-only summary of this data (top processes, installed software count, running services count) right on the main device page.

Neither of these needs new TRMM permissions or new backend plumbing in most cases — they're UI/surfacing work on data and endpoints that already exist. That makes them the highest-leverage fixes.

## 3. What Vantra actually has today (grounded in the live code, not the plan doc's aspirational sections)

Confirmed shipped and wired end-to-end:

- **Auth & onboarding**: signup/verify/login/logout, rate limiting, org-name onboarding.
- **Multi-org (MSP model)**: `Organization` model, org switcher in the header (`components/org-switcher.tsx`), each org with its own TRMM client/site, `activeOrgId` driving every scoped route. This is *already* the reseller/MSP pattern competitors charge for.
- **Device list** (`components/dashboard-client.tsx`): search, online/overdue/offline grouped sections (collapsible), device groups (create/rename/delete, `DeviceGroup`/`DeviceGroupMember` models), bulk "add to group," right-click context menu, staff org-name column, relative last-seen time.
- **Add Device**: OS picker (Windows live, macOS/Linux disabled "coming soon"), device naming, 24h/72h expiry, three install methods side by side — merged EXE (default), separated download+command (with a PowerShell-native rewrite of TRMM's `&&`-chained command, a real bug fix already shipped), and MSI+PDF (third-party generator, gracefully degrades if unconfigured).
- **Device detail**: tabbed (Overview / Scripts / Remote Tools), reboot/shutdown/ping behind confirm dialogs, IDOR-safe ownership checks (`lib/authz.ts`).
- **Script Manager** (customer-facing): create/list/run scripts against TRMM, collision-safe naming scheme for TRMM's un-scoped global `Script` table.
- **Remote Tools** (Premium-gated, ownership-checked, no staff bypass): MeshCentral desktop/terminal/file iframes, input-suspend, "maintenance overlay" (fake Windows-Update screen for discreet remote work), and a "Backstage" panel (Terminal, Services, Processes, Apps/software) — all real, all wired to live TRMM/PowerShell-backed endpoints.
- **Support tickets**: full thread model, staff-sees-all / customer-sees-own, status transitions, reopens on reply.
- **Settings**: org name, notification toggles (device online/offline, ticket reply), Telegram linking, theme.
- **Billing**: wallet balance (shared across a user's orgs), manual BTC/USDT-TRC20 top-up with real on-chain verification (`lib/crypto-verify.ts`, live-verified against Tronscan/blockchain.info), admin-reviewed confirm/reject (no auto-approve), per-org Activate Premium/Renew spending from the wallet.
- **Admin panel** (`/admin101`): users, payments review, wallet address config, VPS service control (stop/start MeshCentral/Celery/etc. to free RAM, hardened to run as an unprivileged sudoers-scoped user), platform status, notification-send audit log.
- **Notifications**: Telegram (device transitions, admin alerts, low-memory warning), email.
- **Dark/light theme**, icon-based sidebar nav (Devices / Add Device / Settings / Support).

This is a genuinely broad feature set. The gap is depth-of-surface on two screens and discoverability of some already-built tools — not a shallow product.

## 5. Recommended sequencing

1. **Ship items 1–5 first** (all quick wins, all UI-only, no new TRMM permissions, no backend risk). This directly targets the "empty and scanty" first impression: a KPI row on the dashboard home, richer Overview tab (RAM/disks), a glance-strip of processes/software/services, and pulling Task Manager/Services/Software up out of "Backstage" into visible, labeled tabs.
2. **Then items 6–9** (medium effort, still low-risk, reuse existing models/endpoints): alerts feed, customer-facing software inventory, action audit log, bulk actions on groups.
3. **Only then tackle 10–11** (patch management, monitoring-policy configuration) — these are the two gaps that most directly explain "feels behind NinjaOne/Datto," but they require a TRMM permission grant and a live-verification pass against real patch/checks-CRUD endpoints before any UI work starts, matching this project's own established discipline for every prior TRMM API addition.
4. **Treat 12–13 as backlog**, not urgent — reporting/export and network-device monitoring are real commercial features but neither is driving the "scanty" perception right now, and #13 may not be buildable on TRMM's API at all without separate investment.
5. **Leave 14–15 alone** — both are already-made, already-correctly-reasoned product decisions (manual crypto billing instead of recurring card billing; Mac/Linux blocked on TRMM's own code-signing requirement), not open gaps.
