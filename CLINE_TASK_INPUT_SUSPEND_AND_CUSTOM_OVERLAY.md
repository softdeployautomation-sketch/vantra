## 3. Custom maintenance-overlay assets — genuinely new feature

Confirmed with the user: the default Windows-Update-style overlay (`lib/maintenance-overlay.ts`'s `GUI_SCRIPT` — dark screen, marquee spinner, "Working on updates" / "Don't turn off your computer") stays as the **default, built-in option**. New ask: let the technician **upload a custom image, PNG, or animation (GIF)** to show over the *guest's* screen instead, when starting the maintenance overlay — the same "hide what I'm doing from the person at the desk" purpose, just with a custom visual instead of (or as an alternative to) the fake Windows Update look. The user's own words confirm the target surface is unchanged (it shows on the guest's screen, never the technician's — that's already inherent in how the overlay works today, since it's a script that runs and renders on the remote device itself).

### Recommended approach (your call on exact implementation, but this avoids inventing new infrastructure)

`sendRawCmd`/`startMaintenanceOverlay` already delivers the *entire* overlay script to the device as one base64-encoded blob embedded in a PowerShell launcher command (see `launcherCommand()` in `lib/maintenance-overlay.ts` — `Buffer.from(GUI_SCRIPT, "utf8").toString("base64")`, decoded and run agent-side via `Start-Process`). The simplest way to deliver a custom image with **no new file-transfer mechanism** is to embed the uploaded image's own bytes as a *second* base64 blob inside that same generated script, and have the WinForms script decode it into a `System.Drawing.Image` (via `[System.Drawing.Image]::FromStream((New-Object IO.MemoryStream(,$bytes)))`) and display it full-screen in a `PictureBox` (`SizeMode = 'Zoom'` to preserve aspect ratio, or `'StretchImage'` to fill exactly — your call, `Zoom` is probably the safer visual default) instead of the drawn spinner/text.

Concrete pieces:
1. **`startMaintenanceOverlay(agentId, opts?)`** in `lib/maintenance-overlay.ts` — widen the signature to accept an optional `{ customImageBase64?: string; customImageExt?: "png" | "gif" | "jpg" }`. When present, generate a *different* GUI script variant (a `PictureBox`-based one) instead of the current hardcoded `GUI_SCRIPT`; when absent, behave exactly as today (no change to the default path).
2. **GIF animation**: PowerShell/WinForms *can* animate a multi-frame GIF via `[System.Windows.Forms.Application]::Idle` + `[System.Drawing.ImageAnimator]::Animate(...)`/`UpdateFrames(...)` — **verify this actually works cleanly on a real Windows test agent before shipping it as a feature**, same "verify before trusting" discipline as every other live-executing script change in this project (the reboot/shutdown/`run_as_user` GUI-visibility items were deliberately deferred to a live test for the same reason). If it turns out flaky/not worth the complexity, a static-image-only version (PNG/JPG, first-frame-of-GIF fallback) is a legitimate, honestly-scoped fallback — flag that tradeoff back rather than shipping something that silently doesn't animate.
3. **Size cap**: `sendRawCmd`'s payload travels over the same synchronous NATS round-trip as every other command this project sends — base64 inflates by ~33%, and there's no established message-size ceiling documented anywhere in this codebase yet. **Verify the actual practical limit** (send an increasingly large test payload against a real test agent, find where it starts failing, or check TRMM/NATS source for an explicit cap) before picking a cap — a reasonable starting guess is 1–2MB for the original image (before base64 inflation), enforced both client-side (reject the file before upload) and server-side (reject the request), but confirm this against reality rather than shipping an arbitrary number blind.
4. **Upload UI**: check whether an existing upload pattern already exists in this codebase before inventing a new one — the MSI-generator branding flow (`exeUrl`/`icoUploaded` fields on `Deployment`, mentioned in the schema) suggests there may already be an icon-upload route/component to model this on structurally (multipart form handling, file-type/size validation). If nothing reusable exists, a plain `<input type="file" accept="image/png,image/gif,image/jpeg">` + client-side size/type validation + reading the file into a base64 string via `FileReader` before sending it to a new API route is sufficient — this doesn't need persistent storage on Vantra's own DB/disk (per the "recommended approach" above, the image travels embedded in the one-shot command and isn't stored anywhere after use), so no new Prisma model is needed unless you want to let a technician re-use a previously-uploaded image across sessions (a nice-to-have, not required for this pass — note it as a possible fast-follow rather than building it now).
5. **Where this lives in the UI**: the existing "Start maintenance screen" `PostConnectAction` currently just calls `startMaintenanceOverlay(agentId)` directly on select. Change this one entry into something that, on select, opens a small inline chooser (a `Modal` — reuse `components/modal.tsx`, already used elsewhere in this app — is a good fit) offering: "Default (Windows Update style)" (the existing behavior, call `startMaintenanceOverlay(agentId)` with no `opts`) vs. "Custom image/animation" (shows the file input, then calls `startMaintenanceOverlay(agentId, { customImageBase64, customImageExt })` once a file is chosen). Keep "Stop maintenance screen" as a separate, simple action unchanged (it doesn't need to know which variant was running — `stopCommand()` already just kills by PID file, agnostic to which script wrote it).

### API route

`app/api/devices/[agentId]/maintenance-overlay/route.ts` (existing route wrapping `startMaintenanceOverlay`/`stopMaintenanceOverlay`) needs its `POST` body widened to optionally accept the custom-image fields, validated (file type allowlist, size cap per point 3 above) before being passed through. Same auth gate as today (`authorizePremiumAgentAction` or whatever it currently uses — don't change the authorization model, only the payload shape).
