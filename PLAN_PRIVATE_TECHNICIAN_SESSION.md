# Plan — Private Technician Session (staff-only, premium-only maintenance mode)

**Status: core lifecycle built, not yet live-tested, companion engine not yet built.** The desktop-switch validation spike hasn't been run to completion (test VM stalled) — proceeding on the explicit instruction to assume the underlying OS mechanism works, confirmed later via real testing before this goes near a real device. Built so far: `prisma/schema.prisma`'s `TechnicianSessionLog` model + migration, `lib/technician-session-log.ts` (audit helper), `lib/technician-session.ts` (Prepare/Blank/Restore/Release script generators). NOT yet built: the companion capture+input engine, the relay transport server, the authz gate, API routes, and UI wiring — see "How this gets built" below. Do not hand any of this to Cline yet.

## Why this exists

The existing "Start maintenance screen" feature (`lib/maintenance-overlay.ts`, wired through `components/remote-tools.tsx`'s Tools menu) shows a fake "Working on updates" screen on the guest's machine, but it's a screen-mirroring overlay — MeshCentral's remote-desktop capture follows whatever Windows considers the "current input desktop," so the technician's own remote view goes blank too, the same moment the guest's does. This was root-caused by reading MeshAgent's actual capture source (`meshcore/KVM/Windows/kvm.c`'s `CheckDesktopSwitch`, which explicitly calls `OpenInputDesktop()` every frame) — it's not a bug, it's necessary so the technician's view correctly follows real UAC/lock-screen transitions. Patching that out would break that legitimate behavior and mean forking/maintaining MeshAgent forever.

The real fix needs a second, independent desktop object: switch the guest's *visible* desktop to a decoy carrying the overlay, while a separate, purpose-built process stays pinned to the real desktop and keeps capturing + controlling it for the technician. This is a real, working Windows technique (confirmed via Microsoft's own `SwitchDesktop`/`CreateDesktop` docs and real-world precedent) — but the same mechanism is also the core technique behind HVNC (Hidden VNC) malware, which hides a remote operator's actions from a victim. That's why this is being built as a **staff-only, premium-gated technician capability inside Vantra** (not a customer self-service feature, not shipped as a generic capability) — the access model below is the mitigating control, not an afterthought.

## Rollout phases (per the user's explicit sequencing)

1. **Phase 1 — build + internal test.** Build the feature, gate it to Premium orgs, and validate it end-to-end against our own existing test accounts/orgs (Sblast, Mblast, Michael Test Org — already premium per earlier grants) and the real Windows test agent. No real paying customer sees this during Phase 1.

## Architecture — three separate actions, not one

The key design correction from the original draft: **standing the capability up is not the same as using it.** Creating the decoy desktop and keeping a companion process warm has no visible effect on the guest at all — nothing is blanked until a technician explicitly switches to it. This means the expensive/slow setup work (create desktop, launch companion) can happen well in advance of any actual need, so that the moment a technician *does* want to blank the guest, all that's left to do is a single, near-instant `SwitchDesktop()` call. Three distinct actions, not one combined "start/stop":

1. **Prepare** (fast-trigger setup, no visible effect on the guest): creates the decoy desktop (`CreateDesktop`, e.g. `VantraTechSession`) and launches the companion capture/input process, pinned via `OpenDesktop("Default", …)` + `SetThreadDesktop()`, doing steady BitBlt capture and `SendInput`-based control against the real desktop. The overlay UI is also pre-launched onto the decoy desktop at this point (so it's already rendered and ready, not launched at blank-time). Nothing is switched yet — the guest sees no change whatsoever.
2. **Blank / Restore** (the fast, repeatable toggle a technician actually clicks while working): `SwitchDesktop()` to the decoy (blank) or back to `Default` (restore). Because Prepare already did the slow part, this is near-instant every time — a technician can toggle it back and forth freely during a session with no perceptible delay.
3. **Release** (explicit teardown, ends the standing capability): closes the companion process and the decoy desktop entirely, restores the guest to fully normal operation, and returns the device to ordinary/autonomous monitoring. This is a deliberate action the technician takes when the work is fully done — the device doesn't carry this capability indefinitely.

**Delivery mechanism — reuse the existing pattern, no new agent/installer.** All three actions are one-shot PowerShell scripts (matching the existing overlay's own `Add-Type`-embedded-C#/WinForms technique) sent through `sendRawCmd`/TRMM's `runscript`. Prepare and Blank/Restore need `run_as_user: true` (TRMM's agent runs as SYSTEM/session 0, which can't render UI on or interact with the interactive user's desktop at all — a session-isolation restriction, not a privilege one; SYSTEM is already higher-privileged than Administrator). Release can run either way since it's just teardown.

**Provisioning trigger — start broad and manual, narrow later.** Per explicit instruction: for this first, manually-validated phase, **Prepare fires automatically the moment a device is added**, for devices under a staff/premium-eligible context — not gated behind any ticket/incident logic yet. This is deliberately simple so the mechanism itself can be proven reliable by hand before any smarter automation (e.g. tying Prepare/Release to a support ticket's lifecycle) gets layered on top. Refining *when* Prepare/Release actually fire is future work, explicitly deferred until the core mechanism is proven.

**Safety net (non-negotiable, build this alongside the feature, not after)**: if the companion process crashes, or a technician's browser disconnects while the guest is mid-blank, the device must never get stuck showing the decoy screen forever. Needs a watchdog/timeout (e.g. the agent-side script self-monitors and force-`SwitchDesktop`s back to `Default` after N minutes of no heartbeat) — this is the single most important failure mode to design against before shipping. This applies even more now that Prepare can be standing for a long, open-ended time — the watchdog must guard the *blanked* state specifically (a long-lived-but-not-currently-blanked decoy desktop is harmless; a stuck *blanked* one is the real danger).

**Transport decision (revised)**: not TRMM's own tunnel plumbing after all — that would mean reverse-engineering an internal mechanism we don't control. Instead, mirror SpaceWorker's already-proven `browser-server` architecture exactly: a small, SEPARATE Node service (`technician-session-server/server.ts`, run via `tsx` under its own systemd unit, matching `spaceworker-browser.service`'s shape) that the companion process connects to **outbound** (customer networks are far more NAT/firewall-friendly for outbound connections than inbound — this is also how the TRMM agent itself already calls home). nginx already proxies a WebSocket upgrade to an internal `127.0.0.1`-bound port for SpaceWorker's browser streaming on this same VPS — same proven pattern, new path (e.g. `wss://vantra.instaweb.top/api/technician-session/agent-ws?token=...` for the agent, a separate viewer-side path for the browser). The relay pipes binary JPEG frames one way (companion → browser) and JSON input-command messages the other way (browser → companion) — a small custom protocol, not a full RFB/VNC implementation, since we don't need general VNC compatibility, only our own two endpoints talking to each other. Companion-side: a raw TCP connection out to the relay is simpler to get right in embedded C# than an async `ClientWebSocket`; the relay bridges TCP-from-agent to WebSocket-to-browser (Node handles that natively).

**Audit log**: every Prepare / Blank / Restore / Release must be logged (who or what triggered it — a specific staff member, or "auto-prepare on device add" — which device, which org, timestamps). This is the concrete accountability control that makes "staff can work invisibly on a customer's device" defensible — there must always be a clear record of what happened and when, especially now that Prepare can be automatic rather than always a specific person's deliberate click.

## Open technical question to resolve before building the authz gate

Every existing premium-gated route (`lib/agent-route.ts`'s `authorizePremiumAgentAction`/`authorizePremiumDeviceAction`) checks the **caller's own active organization's** plan. That doesn't work here: staff bypass ownership entirely (they can act on *any* customer's device), so for this feature we need to check the plan of the **target device's owning Organization**, not the staff member's own org. This requires a reverse lookup (agentId → owning Organization → its `plan`) that doesn't fully exist yet — `listAgents()` returns TRMM's own `client_name`/`site_name` strings per agent, not a direct foreign key to our `Organization.id`. Resolve this by matching the agent's TRMM client id (confirm `getAgentDetail`/`listAgents` actually expose a numeric client id, not just a name string — verify against the real API rather than assume) against `Organization.trmmClientId` in our DB. Write a new `getOrganizationForAgent(agentId)` helper in `lib/authz.ts` or `lib/session-user.ts` once this is confirmed, and build the new gate (e.g. `authorizeStaffPremiumTechnicianAction`) on top of it, mirroring the shape of the existing `authorizePremiumAgentAction`.

## Before writing the full pipeline — validate the one real unknown first

Some Windows internals sources suggest DWM composition behaves differently for a desktop that isn't the currently-active one, which could mean modern, hardware-accelerated UI (browsers, the Settings app) doesn't render correctly on the "parked" real desktop once we've switched away from it. This needs a cheap, standalone validation spike (create a second desktop, switch to it, confirm via BitBlt from the original desktop that ordinary apps still render and respond correctly) on a real Windows test agent, **before** committing to building the full companion-process/transport pipeline. Do this spike first.
